# friendlypass browser protocol — ACTIONS

**Status:** FROZEN — protocol version **1** (`protocol/version`).
**Owner:** WP0 (architect). Change control: see §9.
**Date:** 2026-11-24.
**Audience:** every agent implementing the extension (WP2–WP6, WP8), the native
host (WP1) and the Rust protocol server (WP7a/WP7b). Code against this file, not
against memory or upstream blog posts.

This document specifies two layers:

1. **The KeePassXC-Browser wire protocol**, reproduced so the *official*
   keepassxc-browser 1.10.4 extension keeps working against friendlypass, and so
   the new extension can be tested against real KeePassXC as an oracle.
2. **friendlypass extensions** (host-level `ping`/`hello`, push messages, host
   error codes). These are clearly marked **[friendlypass]** and are additive:
   a KeePassXC client never sees them, and an older client must safely ignore
   them.

Normative references, checked at the time of writing:

- KeePassXC C++ `src/browser/` at `cd422365` (2.8.0 line), especially
  `BrowserAction.cpp`, `BrowserMessageBuilder.{h,cpp}`, `BrowserService.cpp`,
  `BrowserHost.cpp`, `BrowserShared.h`.
- keepassxc-browser at `9d27471` (v1.10.4.1), especially
  `background/{client,keepass,event,init,httpauth}.js` and
  `dist/manifest_chromium.json`.
- Golden fixtures in `protocol/fixtures/` generated by
  `protocol/gen-fixtures.mjs`.

Where this document and upstream disagree, **upstream source wins for
KeePassXC-compatible actions**, and this document must be corrected. §9 lists
the observed upstream quirks that implementers are tempted to "fix"; do not.

## 0. Scope, roles and terminology

```
Chrome MV3 service worker  ── native messaging (stdio) ──►  friendlypass-browser-host
                                                                     │
                                                                     │ app socket
                                                                     ▼
                                                          friendlypass app
                                                          (protocol server + GUI)
```

- **Extension**: the browser side. Holds the X25519 session keypair and the
  permanent identification keypair.
- **Host**: `friendlypass-browser-host`, the native-messaging executable
  registered as `org.friendlypass.browser`. It is a *transport and liveness*
  component. It answers `ping`/`hello` locally and forwards every other frame
  unchanged to the app.
- **App**: the friendlypass desktop application. It terminates the protocol
  cryptography, owns the database and sends push messages.
- **Official extension**: keepassxc-browser as shipped by KeePassXC. It speaks
  only the KeePassXC layer; it must never need to know the host exists as
  anything other than a transparent relay.

Requirements use MUST / MUST NOT / SHOULD / MAY as in RFC 2119.

## 1. Transport

### 1.1 Native-messaging framing

The browser ↔ host channel is Chrome/Firefox native messaging over the host's
stdin/stdout.

```
+--------------------------+-----------------------------------------------+
| 4 bytes, little-endian   | N bytes, UTF-8                                |
| uint32 N                 | exactly one JSON object (no BOM, no newline)  |
+--------------------------+-----------------------------------------------+
```

- The length prefix counts **payload bytes only** (not the prefix).
- Payload is UTF-8 encoded JSON. It MUST be a single JSON **object** at the top
  level; arrays, scalars and multiple concatenated objects are invalid.
- **Maximum payload: 1 048 576 bytes (1 MiB) in both directions.** This is
  stricter than the browser limits (host→browser is 1 MiB; browser→host is
  larger) and matches KeePassXC's `BrowserShared::SOCKET_BUFFER_SIZE`.
- A frame with a length prefix greater than 1 MiB MUST be rejected. The host
  MUST discard exactly that many payload bytes, MUST NOT parse them, MUST write
  a host error frame (`errorCode: "1001"`, see §3.6), and MUST stay alive.
- The host MUST NOT write anything to stdout except protocol frames.
  Diagnostics go to stderr. A stray `println!` is a protocol violation and
  Chrome will close the port.
- The host MUST read exactly `N` bytes; a partial read is buffered until the
  frame is complete. Multiple coalesced frames in one read MUST all be
  processed.
- Invalid UTF-8 or invalid JSON is a host error `"1002"`; the host discards that
  frame and continues. It MUST NOT exit.
- The browser may use the term "native byte order" in its documentation; every
  supported target (x86-64/arm64 on macOS, Windows, Linux) is little-endian, so
  the frozen contract is little-endian.

Worked example — the frame for `{"action":"ping"}`:

```
11 00 00 00  7b 22 61 63 74 69 6f 6e 22 3a 22 70 69 6e 67 22 7d
└─ 17, LE ─┘  └────────────── 17-byte UTF-8 payload ──────────────┘
```

The host↔app socket framing is an **internal** concern of WP1/WP7a (the native
host forwards the decoded JSON object unchanged). It is deliberately not frozen
here, except for these invariants (§1.1.1 records the Phase-1 decision):

- cryptography is end-to-end between extension and app; the host MUST NOT
  re-encrypt, decrypt or rewrite `message`/`nonce` fields;
- the host MUST NOT inject, drop or reorder fields inside a forwarded frame;
- `ping`/`hello` are never forwarded to the app, except for the host's own
  status probe described in §1.1.1.

### 1.1.1 App socket framing (decision, Phase 1) **[friendlypass]**

The app socket is **not** native messaging. It is a Unix stream socket
(`<user temp dir>/org.keepassxc.KeePassXC.BrowserServer` by default) on which
both directions carry **raw, concatenated, compact JSON objects** — exactly what
KeePassXC's `BrowserServer` and `crates/friendlypass-browser/src/server.rs`
speak:

```
{...object 1...}{...object 2...}           no length prefix, no separators
```

Rules:

- Payloads are UTF-8 JSON **objects**; objects are delimited by brace counting
  with string/escape awareness, not by newlines or a length prefix.
- Maximum object size is 1 MiB, the same cap as §1.1. A peer that exceeds it is
  answered with a `1001` host error frame and the object is discarded.
- An object that is not valid JSON, or is valid JSON but not an object, is a
  protocol violation: the host answers `1002` (§3.6) and keeps both links alive.
  It MUST NOT forward an unparseable payload to the browser.
- The host derives the path from the same function the app uses
  (`friendlypass_browser::browser_server_path()`); it MUST honour the
  `FP_APP_SOCKET` environment variable so tests and a relocated app never touch
  the user's real socket. The app also honours `FP_APP_SOCKET`.
- Liveness: the host writes `{"action":"ping"}` once per second and expects the
  app's §5.2-shaped answer. Any answer means "alive"; `appVersion`/`locked`/
  `databaseHash` populate the cached status. Two consecutive unanswered probes
  (1 s timeout each) drop and reconnect the app link.
- The app MUST answer `ping` immediately even while another request on the same
  connection is still being processed (for example `associate` waiting for the
  approval dialog); other requests keep their per-connection order.
- The host MAY push an unsolicited §5.2-shaped `ping` frame to the extension
  when `appRunning` changes, but only after the client opted in with
  `hello.statusPush: true` (§5.3). KeePassXC clients never receive unsolicited
  frames.

This decision keeps KeePassXC-compatible raw-JSON framing rather than the
length-prefixed framing an earlier harness sketch assumed.

### 1.2 Backpressure and ordering

- Frames are independent; the protocol has no multiplexed channels. A client
  MUST correlate replies by `action` and nonce (§2.3), not by arrival order.
- The host SHOULD preserve request order per `clientID`, but the protocol does
  not require it. `generate-password` replies asynchronously and may overtake
  later replies, so clients MUST tolerate out-of-order responses.
- A client MUST have at most a small bounded number of in-flight requests per
  action. Upstream KeePassXC serialises password-generator requests (a second
  one is rejected with error 6).

### 1.3 Unicode and JSON encoding rules

- No `\u` escaping is required beyond what JSON mandates; UTF-8 passes through
  unchanged. Passwords are **not** ASCII-escaped, Base64-encoded or
  HTML-escaped inside the encrypted message.
- Numbers: `count` is a JSON number; most KeePassXC scalar fields that represent
  booleans/codes are JSON strings (`"true"`, `"false"`, `"1"`, `"8"`). Match the
  examples exactly.
- Field names are case-sensitive.
- Unknown fields MUST be ignored on receipt (forward compatibility).

## 2. Cryptography

### 2.1 Primitives and sizes

| Item | Value |
|---|---|
| Key agreement | X25519 (Curve25519) |
| AEAD | XSalsa20-Poly1305 (`crypto_box_easy` / `nacl.box`) |
| Public/secret key | 32 bytes, Base64 |
| Nonce | 24 bytes, Base64 |
| Ciphertext | `Poly1305 tag (16 bytes) || ciphertext`, Base64 |
| Base64 alphabet | standard RFC 4648 with `+`, `/`, `=` padding |
| Plaintext | UTF-8 JSON, compact serialization (no insignificant whitespace) |

`nacl.box(m, n, pk, sk)` produces exactly libsodium
`crypto_box_easy(c, m, mlen, n, pk, sk)`. The Rust crate's
`crypto::seal/open` are compatible; `protocol/fixtures` prove it byte-for-byte.

The plaintext **contains credentials**. Never log a decrypted inner message,
never put one in `chrome.storage`, never send one to a content script except the
specific entry being filled.

### 2.2 Session keys and the handshake

Two keypairs exist per association:

| Keypair | Lifetime | Secret leaves the extension? | Purpose |
|---|---|---|---|
| **Session keypair** | One native connection / handshake | No | Encrypts this session's traffic |
| **Identification keypair** | Permanent (stored in `chrome.storage.local`) | No; only its public half is sent | Proves "this browser was associated" on later sessions |

The app also generates a **host session keypair** per `change-public-keys`.

`change-public-keys` is the only KeePassXC action that is not encrypted:

```json
{
  "action": "change-public-keys",
  "publicKey": "<Base64 32-byte client session public key>",
  "nonce": "<Base64 24-byte request nonce>",
  "clientID": "<Base64 24-byte client id>"
}
```

Successful reply:

```json
{
  "action": "change-public-keys",
  "version": "2.8.0",
  "success": "true",
  "nonce": "<Base64 incremented request nonce>",
  "publicKey": "<Base64 32-byte host session public key>"
}
```

Client verification (all MUST hold):

1. `success === "true"` and `publicKey` decodes to 32 bytes;
2. `nonce` decodes to 24 bytes and equals the request nonce incremented once
   (§2.3);
3. the connection's `clientID` was accepted. KeePassXC keys its per-client
   `BrowserAction` state by `clientID` and silently drops frames with an empty
   `clientID`, so **every** outer frame MUST carry the same non-empty
   `clientID` for the lifetime of the connection.

A new `change-public-keys` always resets the app's association flag for that
`clientID` (§4.3/§4.4). Therefore after every handshake the client MUST run
`get-databasehash` and `test-associate` (or `associate`) before any credential
action.

### 2.3 Nonce rule

- Each **request** chooses a fresh 24-byte nonce `N`, Base64-encoded. It is used
  both for sealing the request and carried in the outer frame.
- The **response** is sealed with `increment(N)` and the outer frame carries
  that incremented value.

Increment is libsodium `sodium_increment`: treat the 24 bytes as a
little-endian integer and add 1, propagating carry:

```
c = 1
for i in 0..24:
    c += nonce[i]
    nonce[i] = c & 0xFF
    c >>= 8
```

Examples: `…00` → `…01`; `…FF` → `…00` with carry into byte 1.

Consequences implementers must respect:

- a client MUST reject a success response whose `nonce` is not exactly
  `increment(request nonce)`;
- a client MUST NOT reuse a nonce for two different plaintexts with the same
  session keys;
- **error replies carry no nonce** (§3.3); correlate them by `action`;
- **[friendlypass]** host-level `ping` echoes its nonce verbatim, which is a
  different rule from the encrypted nonce. `hello` has no nonce (§5).

### 2.4 Association keyring

After a successful `associate`, the extension stores, keyed by the database
hash:

```json
{
  "<db hash>": {
    "id": "chrome-work-laptop",
    "key": "<Base64 identification public key>",
    "hash": "<db hash>",
    "created": 1763925600000,
    "lastUsed": 1763925600000
  }
}
```

- `id` is the user-visible association name returned by the app.
- `key` is the identification **public** key. The secret half never leaves the
  extension.
- The keyring is stored by database hash. A new root UUID (new/recreated/
  restored database) invalidates all associations; the client must re-associate.
- The extension SHOULD persist a stable `clientID` for diagnostics and host
  logging. Upstream regenerates it on every handshake; the app must not use
  `clientID` for authentication.

### 2.5 Replay and failure behaviour

- Decryption failure (wrong key, wrong nonce, truncated/corrupt Base64, invalid
  inner JSON) maps to error **4** (`Cannot decrypt message`) in an unencrypted
  error reply.
- There is no per-frame sequence number beyond the response nonce. A client
  that receives a duplicate response should ignore it once its pending request
  is settled.
- All errors are fail-closed: on any doubt, do **not** send a request in
  plaintext and do **not** fill credentials into a page.

## 3. Envelopes

### 3.1 Outer request (encrypted actions)

```json
{
  "action": "get-logins",
  "message": "<Base64 ciphertext of the inner request>",
  "nonce": "<Base64 24-byte request nonce>",
  "clientID": "<Base64 24-byte client id>",
  "requestID": "<optional, generate-password only>",
  "triggerUnlock": "true"
}
```

- `triggerUnlock` is optional and always the string `"true"` when present. It
  asks the app to raise its unlock UI if the database is locked.
- `requestID` is optional; KeePassXC only echoes it in `generate-password`
  errors. Clients that send one SHOULD be prepared not to get it back from
  older servers.
- `message` and `nonce` are omitted only for `change-public-keys` and for
  **[friendlypass]** host-level actions.

### 3.2 Outer success reply

```json
{
  "action": "<same action>",
  "message": "<Base64 ciphertext of the inner response>",
  "nonce": "<Base64 incremented request nonce>"
}
```

There is no `success` field in the outer envelope; success is encoded by the
presence of `message` and by the inner `success` field.

### 3.3 Outer error reply (unencrypted)

```json
{
  "action": "get-logins",
  "errorCode": "8",
  "error": "KeePassXC association failed, try again"
}
```

- `errorCode` is a **JSON string** (`QString::number(code)` upstream), even
  though the client's error table is numeric. Parse it with `parseInt`.
- `error` is an English human-readable message. Its exact text is not
  normative and may be localised; clients MUST branch on `errorCode`.
- There is **no `nonce` and no `message`**. Correlate by `action`; if several
  requests of the same action are in flight, reject/settle the oldest pending
  one and log the ambiguity.
- Error replies apply to encrypted actions only. A host-level action failure
  uses the host error shape (§3.6).

### 3.4 Inner success prefix

Every decrypted successful response starts with:

```json
{
  "version": "2.8.0",
  "success": "true",
  "nonce": "<Base64 incremented request nonce>"
}
```

- `success` is the string `"true"`, not a boolean.
- `version` is an opaque feature-gating version. Clients parse it as
  `major.minor.patch` and enable features as follows (keepassxc-browser
  `updateFeaturesList`):

  | Minimum | Feature |
  |---|---|
  | 2.6.0 | Browser integration baseline |
  | 2.6.1 | `get-totp` (`newTotp`) |
  | 2.7.0 | `generate-password` dialog, `downloadFavicon` |
  | 2.7.7 | Passkeys |
  | 2.7.10 | Passkey default group |

  **friendlypass MUST emit `"2.8.0"`** in `version` so the official extension
  enables all supported features. The real friendlypass version is reported by
  **[friendlypass]** `hello.appVersion`, not here.

### 3.5 Inner error shape inside a decrypted response

KeePassXC puts ordinary failures in the outer unencrypted error envelope
(§3.3), not inside a decrypted success. The one exception is `set-login`, whose
inner `error` field carries `"success"`/`"error"` while `success` remains
`"true"` (§4.6). Clients MUST handle both places.

### 3.6 Host error frame **[friendlypass]**

```json
{
  "action": "",
  "error": "Message exceeds the 1 MiB frame limit",
  "errorCode": "1001",
  "hostError": true
}
```

- Same envelope as §3.3 plus `"hostError": true`, so one parser handles both.
  Host-originated frames always set this marker, even when they reuse a
  KeePassXC code (for example code 5 when the app is unavailable).
- `action` is the request action when the host could read it, otherwise `""`.
- Codes are 1000+ (§5.6) and never collide with KeePassXC codes.
- The host MUST keep the process alive after emitting one.

### 3.7 KeePassXC error codes (frozen)

Values are wire values. `errorCode` is serialised as a string.

| Code | Name | Meaning |
|---:|---|---|
| 0 | `UNKNOWN_ERROR` | Generic/unknown; not emitted by C++ 2.8.0 |
| 1 | `DATABASE_NOT_OPENED` | No unlocked database (or missing `id`/`key` in test-associate) |
| 2 | `DATABASE_HASH_NOT_RECEIVED` | Server could not produce a database hash |
| 3 | `CLIENT_PUBLIC_KEY_NOT_RECEIVED` | Encrypted action before handshake |
| 4 | `CANNOT_DECRYPT_MESSAGE` | Message/nonce/key/JSON invalid |
| 5 | `TIMEOUT_OR_NOT_CONNECTED` | Client-side timeout; hostile to synthesise except as specified |
| 6 | `ACTION_CANCELLED_OR_DENIED` | User denied / generator busy / cancelled |
| 7 | `CANNOT_ENCRYPT_MESSAGE` | Server-side encryption failure |
| 8 | `ASSOCIATION_FAILED` | Unknown id or key mismatch |
| 9 | `KEY_CHANGE_FAILED` | Handshake rejected |
| 10 | `ENCRYPTION_KEY_UNRECOGNIZED` | Keypair generation/recognition failed |
| 11 | `NO_SAVED_DATABASES_FOUND` | No keyring entry |
| 12 | `INCORRECT_ACTION` | Inner action missing/mismatched |
| 13 | `EMPTY_MESSAGE_RECEIVED` | Empty request object |
| 14 | `NO_URL_PROVIDED` | Missing/oversized URL |
| 15 | `NO_LOGINS_FOUND` | No matching entries |
| 16 | `NO_GROUPS_FOUND` | Empty group tree |
| 17 | `CANNOT_CREATE_NEW_GROUP` | Group creation failed/cancelled |
| 18 | `NO_VALID_UUID_PROVIDED` | Malformed UUID |
| 19 | `ACCESS_TO_ALL_ENTRIES_DENIED` | `get-database-entries` denied |
| 20–33 | passkeys errors | Reserved; see `BrowserMessageBuilder.h` |
| 34 | `CANNOT_USE_REFERENCES` | `{REF:…}` in login/password on save |
| 35–37 | passkeys evaluation errors | Reserved |

## 4. KeePassXC actions (normative)

All actions below except `change-public-keys` use the encrypted envelope
(§3.1). Each section gives the **outer** frame, the **decrypted inner request**
and the **decrypted inner response**, plus error cases and the fixture file.

General precondition enforced by KeePassXC (`BrowserAction::processClientMessage`):

- `change-public-keys` and `request-autotype` may run with the database closed.
- every other action requires the app's database to be unlocked; otherwise the
  reply is error **1** (or **3** if no handshake happened yet) and no inner
  message exists.

### 4.1 `change-public-keys`

Fixture: `protocol/fixtures/change-public-keys.json`.

Unencrypted; see §2.2 for the exact request, response and verification rules.

**Errors**

| Code | Condition |
|---:|---|
| 3 | `publicKey` or `nonce` missing/empty |
| 10 | host keypair generation failed |

### 4.2 `get-databasehash`

Fixture: `protocol/fixtures/get-databasehash.json`.

Outer:

```json
{
  "action": "get-databasehash",
  "message": "<encrypted inner>",
  "nonce": "<request nonce>",
  "clientID": "<clientID>",
  "triggerUnlock": "true"
}
```

Inner request:

```json
{
  "action": "get-databasehash",
  "connectedKeys": ["<db hash>", "<db hash>"]
}
```

- `connectedKeys` is deprecated. Upstream sends `Object.keys(keyRing)` and
  KeePassXC ignores it. Servers MUST accept it, clients SHOULD send it for
  KeePassXC compatibility.
- The client does **not** send `hash`. The app injects its own hash into the
  decoded request before dispatch (`BrowserAction::decodeRequest`).
- `triggerUnlock` is optional on the outer frame.

Inner response:

```json
{
  "version": "2.8.0",
  "success": "true",
  "nonce": "<incremented nonce>",
  "hash": "<64 lowercase hex chars>"
}
```

- `hash` = lowercase hex SHA-256 of the dashless RFC 4122 root-group UUID
  (`BrowserService::getDatabaseHash()`), 64 hex characters. It MUST be
  non-empty. An empty hash makes the official client set
  `isDatabaseClosed = true`.
- Optional `oldHash`: legacy keyring migration hint (SHA-256 of
  root-UUID + recycle-bin-UUID). Accepted by the official client; not emitted
  by 2.8.0.

**Errors:** 2 if no hash can be produced; 4 if the inner action is wrong or
decryption fails.

### 4.3 `associate`

Fixture: `protocol/fixtures/associate.json`.

Inner request:

```json
{
  "action": "associate",
  "key": "<Base64 session public key of this connection>",
  "idKey": "<Base64 identification public key>"
}
```

- `key` MUST equal the public key from this connection's
  `change-public-keys`, byte-for-byte. A mismatch is error 8.
- `idKey` is optional for backwards compatibility. If absent, the app stores
  `key` as the identification key. New clients MUST send `idKey`.

Outer `triggerUnlock` SHOULD be `"true"` for associate: the app may need to ask
the user to unlock and name the connection.

Inner response:

```json
{
  "version": "2.8.0",
  "success": "true",
  "nonce": "<incremented nonce>",
  "hash": "<db hash>",
  "id": "chrome-work-laptop"
}
```

- `id` is the association name chosen by the user (KeePassXC shows an input
  dialog, defaulting to suggestions like `chrome-laptop`). It is the key under
  which the app stores the identification key. Ids are chosen by the user and
  may contain any printable characters; clients must treat them as opaque
  strings.
- `hash` is the database hash at association time. The client stores the
  association under it.
- The app persists the association in database metadata (KeePassXC uses
  custom-data keys prefixed `KPXC_BROWSER_`); friendlypass must persist it too.

**Errors**

| Code | Condition |
|---:|---|
| 4 | decryption/inner-JSON failure |
| 6 | user denied / cancelled the association dialog |
| 8 | empty `key`, or `key` ≠ session public key |

### 4.4 `test-associate`

Fixture: `protocol/fixtures/test-associate.json`.

Inner request:

```json
{
  "action": "test-associate",
  "id": "chrome-work-laptop",
  "key": "<Base64 identification public key>"
}
```

Inner response:

```json
{
  "version": "2.8.0",
  "success": "true",
  "nonce": "<incremented nonce>",
  "hash": "<db hash>",
  "id": "chrome-work-laptop"
}
```

- On success the app sets the per-`clientID` association flag. That flag is
  **required** by `get-logins`, `set-login`, `get-totp`,
  `get-database-groups`, `create-new-group` and passkeys.
- It is **per connection and per `clientID`**: after a reconnect or a new
  `change-public-keys`, `test-associate` MUST run again before credential
  actions. This is the most common cause of spurious error 8.

**Errors:** 1 if `id` or `key` missing; 8 if the id is unknown or the key does
not match; 4 on decryption failure.

### 4.5 `get-logins`

Fixture: `protocol/fixtures/get-logins.json` (plain, multiple/expired, httpAuth).

Inner request:

```json
{
  "action": "get-logins",
  "id": "chrome-work-laptop",
  "url": "https://accounts.example.com/login",
  "submitUrl": "https://login.example.com/session",
  "httpAuth": "true",
  "keys": [
    { "id": "chrome-work-laptop", "key": "<Base64 identification public key>" }
  ]
}
```

| Field | Required | Notes |
|---|---|---|
| `id` | no | Active association id; used for database selection |
| `url` | **yes** | Page URL including scheme/path; empty → error 14 |
| `submitUrl` | no | Form action URL when it differs |
| `httpAuth` | no | String `"true"` for Basic/Digest lookups (§5.5) |
| `keys` | **yes** | Full keyring. KeePassXC searches only databases whose stored key matches one of these pairs; an empty list matches nothing → error 15 |

Inner response:

```json
{
  "version": "2.8.0",
  "success": "true",
  "nonce": "<incremented nonce>",
  "count": 1,
  "entries": [
    {
      "login": "alice@example.com",
      "password": "correct horse battery staple",
      "name": "Example account",
      "uuid": "bb710c2f876761bb90748cc271ff8fae",
      "group": "KeePassXC-Browser Passwords",
      "totp": "123456",
      "expired": "true",
      "skipAutoSubmit": "false",
      "stringFields": [{ "KPH: pin": "4921" }]
    }
  ],
  "hash": "<db hash>",
  "id": "chrome-work-laptop"
}
```

Entry fields (`BrowserService::prepareEntry`):

| Field | Type | Presence |
|---|---|---|
| `login` | string | always; **plaintext username** |
| `password` | string | always; **plaintext password** |
| `name` | string | always; entry title |
| `uuid` | string | always; dashless 32-hex RFC 4122 |
| `group` | string | always; group name |
| `totp` | string | only when the entry has a valid TOTP secret |
| `expired` | `"true"` | only when expired |
| `skipAutoSubmit` | `"true"` / `"false"` | when configured by entry/group |
| `stringFields` | array | only when KPH fields are enabled; each item is `{"KPH: name": "value"}` |

Rules:

- Credentials are **plaintext inside the encrypted message**. Base64-encoding
  them is a protocol violation (and a known bug in the current Rust server).
- `count` is a JSON number equal to `entries.length`.
- Entries are sorted by match quality (exact URL, path, host, subdomain);
  preserve server order in the UI.

## 5. friendlypass extensions

Everything in this section is additive and marked **[friendlypass]**. The
official KeePassXC extension never sends or expects these frames. The new
extension and host MUST implement them; the app MAY.

### 5.1 Version negotiation

- `protocol/version` contains `1`.
- The host reports `protocolVersion: 1` in `ping`/`hello`.
- A client MUST refuse to operate when `protocolVersion` is lower than its own
  required version (currently 1).
- Additive fields do not bump the version. Removing/renaming a field, changing
  a type, or changing crypto/framing does.

### 5.2 `ping` — host liveness and app status

Answered by the host, unencrypted, **even when the app is down**.

Request:

```json
{ "action": "ping", "nonce": "<optional Base64 nonce>" }
```

Response:

```json
{
  "action": "ping",
  "success": "true",
  "protocolVersion": 1,
  "hostVersion": "0.1.0",
  "appRunning": false,
  "appVersion": null,
  "locked": null,
  "databaseHash": null,
  "appTrusted": null,
  "browser": { "kind": "chrome", "verified": true },
  "nonce": "<echo of the request nonce, if sent>"
}
```

Rules:

- **[friendlypass]** `appTrusted` and `browser` are additive fields (host-identify
  §2, host-side check §4). `appTrusted` is the app's answer to the host's
  `host-identify` frame: `true` only when the app verified that its socket peer
  is our host binary, `false` when it did not (including an app that does not
  implement the action), `null` before the reply or while no app is connected.
  `browser` is `{kind, verified}` for the browser that launched this host, with
  `kind` one of `chrome|chromium|brave|edge|firefox|unknown`; the detailed
  `executable`/`teamId` values are host↔app only. The `browser` claim is
  advisory outside the app: auto-approval already required the app to trust the
  peer, so a client only needs `appTrusted`.
- The host MUST answer within 100 ms and MUST NOT block on the app socket.
- The echoed `nonce` is **not** incremented; it is an RTT probe.
- `appRunning` is true only when the host has a live app socket and the app
  answered its most recent status probe (≤ 5 s old). `locked`/`databaseHash`
  are cached values and may lag; null means unknown.
- Heartbeat: every 20 s, 3 s timeout, 2 consecutive misses → destroy the port
  and reconnect (§6).
- If the request is not valid JSON, the host answers with a host error (§3.6).

### 5.3 `hello` — connection negotiation

Answered by the host, unencrypted, at connection start. Richer than `ping` but
carries no nonce and does not change state.

Request:

```json
{
  "action": "hello",
  "clientID": "<optional Base64 client id>",
  "extensionVersion": "0.1.0",
  "statusPush": true
}
```

`statusPush` is optional and additive. When it is `true`, the host MAY write an
unsolicited `ping` frame (the §5.2 shape, no `nonce`) whenever `appRunning`
changes, so the extension updates its status and starts recovery without
waiting for the 20 s heartbeat. A host that does not implement it ignores the
field; a client that does not send it keeps a strict request/reply stream.

Response:

```json
{
  "action": "hello",
  "success": "true",
  "protocolVersion": 1,
  "hostVersion": "0.1.0",
  "appRunning": true,
  "appVersion": "0.1.0",
  "locked": true,
  "databaseHash": null,
  "appTrusted": true,
  "browser": { "kind": "chrome", "verified": true },
  "sessionId": "7b1d0c5e-4a2f-4f6e-9c3b-2d1a0e8f6b4c",
  "hostPid": 4242
}
```

- **[friendlypass]** `appTrusted` and `browser` are the same additive fields as
  in `ping` (§5.2), with the same meaning and nullability. They are repeated
  here so a client that only sends `hello` sees them without a second request;
  the unsolicited `appRunning` status frames allowed by `statusPush` below use
  the `ping` shape and therefore carry them too.
- `sessionId` is host-generated and stable for the stdio connection. It is for
  diagnostics only, not authentication.
- `hello` MUST NOT trigger a database unlock or any GUI action.
- A client that sees `appRunning: false` stays connected (the host stays alive)
  and shows "friendlypass not running"; it MUST NOT spin on `connectNative`.

### 5.4 App → extension push messages

Unencrypted, no nonce, no correlation. They may arrive at any time, including
between a request and its response. Primitive parsers MUST check for a known
push `action` before treating a frame as a response.

```json
{ "action": "database-locked" }
```

```json
{ "action": "database-unlocked" }
```

```json
{ "action": "database-changed", "hash": "<optional new db hash>" }
```

- `database-locked` / `database-unlocked` are KeePassXC-compatible messages
  (`BrowserService::databaseLocked/Unlocked` broadcasts them to every socket).
  The official extension reacts by re-running `test-associate`; while locked
  that fails, which is how its UI learns the state.
- `database-changed` is **[friendlypass]** only: emitted after a save/update,
  database switch or metadata change. It carries the new hash when it changed.
- Pushes do **not** invalidate session keys or the association. On
  `database-unlocked` (or after app restart) the client MUST re-run
  `get-databasehash` and `test-associate` because the hash may have changed.
- Clients that do not know a push `action` MUST ignore the frame.

### 5.5 `get-http-auth` — usage note

There is **no separate wire action**. HTTP Basic/Digest lookups reuse
`get-logins` with `"httpAuth": "true"`:

```json
{
  "action": "get-logins",
  "id": "chrome-work-laptop",
  "url": "https://intranet.example.com/",
  "httpAuth": "true",
  "keys": [{ "id": "chrome-work-laptop", "key": "<…>" }]
}
```

Behaviour the app implements (KeePassXC `BrowserService::findEntries`):

- Entries/group custom data `BrowserOnlyHttpAuth` are excluded from normal
  form lookups but included for HTTP auth; `BrowserNotHttpAuth` is excluded from
  HTTP auth.
- HTTP auth matches always require user confirmation unless the app setting
  "always allow" for HTTP auth is enabled. The extension must therefore expect
  a slower reply and use a long timeout (30 s).
- There is **no `realm` field on the wire in 2.8.0**. The extension may use the
  realm in its own picker, but cannot send it. (KeePassXC stores a realm in entry
  config; `get-logins` does not transmit it.)
- Only Basic and Digest can be answered. NTLM/Negotiate, client certificates
  and OS-handled auth are out of scope.
- The extension's `onAuthRequired` handler MUST:
  - register synchronously at service-worker top level;
  - call the browser callback exactly once, with an 8 s hard deadline that
    falls back to `{ cancel: false }`;
  - keep a per-`requestId` map and never retry the same credentials after the
    browser re-challenges (loop guard);
  - match on `https://host[:port]/` (or `http://`), and for proxy auth use the
    challenger/proxy host; `tabId` may be `-1`;
  - treat "no match", "host down" and "timeout" identically: `{cancel:false}`.

### 5.6 Host error codes **[friendlypass]**

| Code | Name | When |
|---:|---|---|
| 1001 | `FRAME_TOO_LARGE` | Length prefix > 1 MiB; body discarded |
| 1002 | `MALFORMED_FRAME` | Invalid UTF-8/JSON or non-object payload |
| 1003 | `UNKNOWN_HOST_ACTION` | Unencrypted action the host does not implement |
| 1004 | `HOST_INTERNAL_ERROR` | Unexpected host failure |
| 1005 | `APP_UNAVAILABLE` | App socket down past the forwarding grace period |
| 1006 | `ENCRYPTION_REQUIRED` | Host-level action received where crypto is required |

For 1005 the host SHOULD use the KeePassXC-compatible code **5** instead when
the failed request was an encrypted app action, so stock clients treat it as a
transient connection failure. 1005 is reserved for diagnostics callers.

### 5.7 Reserved: `launch-app`

Reserved name for a future user-initiated "start friendlypass" action. Not in
protocol 1. The host MUST NOT auto-launch the app without an explicit user
gesture from the extension.

## 6. Extension connection state machine

Reproduced from REPORT §7.1 and made normative for the TypeScript background.

```
DISCONNECTED ──connect──► CONNECTING ──port open──► HANDSHAKING ──ok──► READY
     ▲                        │                        │                 │
     │                        └──── error/timeout ─────┘                 ├── database-locked ──► LOCKED
     │                                                                    │
     └──────────── port lost (reject pending, schedule backoff) ◄─────────┘
                                      ▲
                                      └── LOCKED ── database-unlocked ──► HANDSHAKING
```

### 6.1 States

| State | Meaning | Invariants |
|---|---|---|
| `DISCONNECTED` | No native port. | No request may hang; all pending are rejected with code 5. |
| `CONNECTING` | `connectNative()` called, waiting for the port. | `connect()` is idempotent; only one attempt at a time. |
| `HANDSHAKING` | Port open; `hello` + (`change-public-keys` → `get-databasehash` → `test-associate`) running. | No encrypted action may be sent before `serverPublicKey` exists. `ensureSession()` is serialised. |
| `READY` | Port open and host reachable. When the app is up, session keys and an association are established; when it is down, only `ping`/`hello` are usable until it returns. | Credential actions only run while `appRunning` and the session is established; otherwise they fail fast with code 1/5. |
| `LOCKED` | App reachable but database locked (push or error 1). | Port and keys stay; `database-unlocked` returns to `HANDSHAKING` to revalidate. |

`READY` carries an `appRunning` flag rather than a separate state: the host is
deliberately kept alive when the app is down (Chrome ≥ 105 keeps the service
worker alive while a native port is open, which removes the wake/race class).
A `ping` that flips `appRunning` from false to true moves `READY` back to
`HANDSHAKING`, so recovery needs no user action.

### 6.2 Transitions and triggers

| From | Event | To | Action |
|---|---|---|---|
| `DISCONNECTED` | `connect()` (SW start, `onStartup`, `onInstalled`, alarm, user) | `CONNECTING` | `connectNative`; start 10 s connect guard |
| `CONNECTING` | port opens | `HANDSHAKING` | send `hello`; start handshake |
| `CONNECTING` / `HANDSHAKING` | `hello` reports `appRunning: false` | `READY` | keep the port open; no keys yet; retry handshake when `ping` reports the app up |
| `READY` (app down) | `ping` reports `appRunning: true`, or a user/tab action needs credentials | `HANDSHAKING` | run the handshake now |
| `CONNECTING` | port error / host exit | `DISCONNECTED` | schedule backoff |
| `HANDSHAKING` | `change-public-keys` + `get-databasehash` OK | `READY` | reset backoff, persist hash, run `test-associate` |
| `HANDSHAKING` | any handshake error/timeout | `DISCONNECTED` | schedule backoff (unless error 1 → `READY`/`LOCKED`) |
| `READY` | `database-locked` push, or error 1 from any action | `LOCKED` | clear login caches, update UI |
| `LOCKED` | `database-unlocked` push | `HANDSHAKING` | re-run `get-databasehash` + `test-associate` |
| `READY` / `LOCKED` / `HANDSHAKING` | port lost (`onDisconnect`, 2 missed heartbeats) | `DISCONNECTED` | reject pending with code 5, backoff |
| any | `disconnect()` (extension reload/shutdown) | `DISCONNECTED` | close port, clear timers |

### 6.3 Timers and limits

| Rule | Value |
|---|---|
| Reconnect backoff | 500 ms, 1, 2, 4, 8, 15, 30 s (cap), reset on `READY`; add ±20 % jitter |
| Watchdog | `chrome.alarms`, every 30 s (Chrome minimum); if `DISCONNECTED`, call `connect()` |
| Heartbeat | `ping` every 20 s, 3 s timeout; 2 consecutive misses → destroy port |
| Default request timeout | 10 s |
| Long request timeout | 30 s (`set-login`, unlock-triggering actions, HTTP auth, `generate-password`) |
| `ensureSession()` | one shared promise; 20 tabs waking at once cause one handshake |
| Pending requests on port loss | rejected with code 5; never left hanging |
| `connect()` calls | idempotent; repeated calls join the in-flight attempt |

### 6.4 Hard client rules

1. Never send an encrypted action while `serverPublicKey` is unknown or stale
   after a new handshake.
2. Never send plaintext credentials, and never accept a response without a
   matching incremented nonce (except errors/pushes).
3. Never expose a "connected" UI based only on `connectNative()` succeeding;
   `appRunning`/`READY` require a successful `hello`/handshake.
4. Every request settles: value, typed error, or timeout. No unhandled
   rejection.
5. After `change-public-keys` (including an SW restart) always run
   `test-associate` before credential actions.

## 7. Compatibility and conformance

### 7.1 Official extension as oracle

The official keepassxc-browser 1.10.4.1 MUST fill and save against a
friendlypass server. To keep that true:

- emit `errorCode` as a **string**;
- emit `success` as the **string** `"true"`;
- return **plaintext** `login`/`password`;
- return a non-empty 64-hex `hash` for `get-databasehash`;
- echo a valid incremented nonce on every encrypted success;
- return `groups` nested as `{groups:[…]}`;
- accept `connectedKeys`, `keys`, `triggerUnlock`, `requestID` and unknown
  fields;
- never require the client to send `hash` inside an inner request.

### 7.2 New extension as oracle

The new extension SHOULD work against real KeePassXC 2.6.1+ (native messaging
via the real `keepassxc-proxy`) for the actions above. It must therefore not
depend on friendlypass-only fields when talking to KeePassXC, and must tolerate:

- no `ping`/`hello` (host absent / KeePassXC proxy): the connection then relies
  on `change-public-keys` and the legacy timeouts;
- `{}` frames from `generate-password`;
- `oldHash` or its absence;
- server error strings in any locale.

## 8. Assumptions recorded (WP0)

These were decided while writing this contract. They are normative until
changed by the architect.

1. **Framing endianness:** little-endian on all targets (browser docs say
   "native byte order"; every supported platform is LE).
2. **Frame cap:** 1 MiB in both directions, stricter than the browser's
   browser→host limit.
3. **Inner `version`:** friendlypass emits `"2.8.0"` for feature gating; the
   real app version is exposed via `hello.appVersion`.
4. **Association state is per connection and per `clientID`.** Clients must
   re-run `test-associate` after every handshake. A stable clientID is
   recommended but not used for authentication.
5. **`get-database-groups` keeps the nested `{groups:{groups:[…]}}` shape** for
   compatibility with the official extension, even though it is awkward.
6. **`generate-password` is asynchronous** and may emit a bare `{}` frame
   first. No 500 ms timeout.
7. **`ping`/`hello` are host-level, unencrypted, and never forwarded** to the
   app. They are not part of the KeePassXC protocol.
8. **Error strings are non-normative**; clients branch on numeric codes.
9. **`realm` is not on the wire** for `get-logins` in 2.8.0.
10. **Host may synthesise error 5** when the app is unavailable, so stock
    clients retry.
11. **Official extension never sends `ping`/`hello`**; the host must not require
    them to relay KeePassXC traffic.
12. **Phase 1 excludes** passkeys, global Auto-Type, `create-new-group`,
    `delete-entry`, `get-database-entries` and multiple simultaneously open
    databases. Their names are reserved.
13. **Credentials are plaintext inside the ciphertext.** This is not negotiable
    for KeePassXC compatibility. Security comes from the AEAD and the
    association, not from encoding.
14. **Protocol version 1** is the only version currently defined; unknown
    fields are ignored, and additive changes do not bump it.

## 9. Change control

`protocol/ACTIONS.md`, `protocol/version` and `protocol/fixtures/*.json` are
frozen and owned by the architect (WP0). Any change requires:

1. a written note in this file explaining why KeePassXC compatibility is
   preserved or intentionally broken;
2. regenerating fixtures with `node protocol/gen-fixtures.mjs`
   (`tweetnacl` from `extension/node_modules`);
3. a protocol version bump for breaking changes, plus an update to
   `extension/src/common/types.ts` and `SUPPORTED_PROTOCOL_VERSION`;
4. review by the owners of every affected work package
   (`protocol/OWNERSHIP.md`).

Known upstream quirks that MUST NOT be "fixed" silently:

- outer `errorCode` is a string;
- `get-database-groups` is double-wrapped;
- `set-login` reports success in the inner `error` field;
- inner requests do not contain `hash`; the server injects it;
- error replies are unencrypted and carry no nonce;
- `change-public-keys` response nonce is incremented;
- `clientID` is required on every frame and keys per-client state;
- `generate-password` may answer asynchronously and may emit `{}`.
